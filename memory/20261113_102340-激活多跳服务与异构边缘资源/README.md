# 激活多跳服务与异构边缘资源

## 对话目标

通过显式服务部署约束和逐边缘异构算力矩阵，构造接入边缘服务未命中、远端边缘计算更有收益的场景压力，使多跳路径成为有效决策维度；同时保持空时隙任务可行率和任务完成率。

## 已完成事项

- 先更新数学模型中的服务部署、异构资源和 deadline 假设，再修改代码、配置、测试和其他文档。
- 用配置字段 service_deployment 替换候选生成中的随机取模服务规则。
- 云端继续隐式部署全部五类服务；边缘候选必须满足显式服务矩阵。
- 用 edge_speed_matrix 替换所有边缘共享同一算力向量的实现。
- 边缘 0、3 配置为 NPU 强的 [150,500,150]，边缘 1、4 配置为 FPGA 强的 [150,150,500]，边缘 2、5 配置为 CPU 均衡的 [400,200,200] GFLOP/s。
- deadline 参考计算使用全局最慢边缘资源 150 GFLOP/s，松弛区间从 [1.2,2.5] 调整为 [1.8,3.0]。
- 新增服务部署回归测试，验证接入边缘缺少服务时，只生成远端已部署服务的边缘候选或云端候选。
- 保留标准最短路径传统基线，没有为了提高多跳指标而修改其定义。
- 工作区中并行存在的 CPU/GPU 默认设备、环境文件和训练记录改动已保留并一并验证。

## 服务部署矩阵取舍

截图建议让边缘 2、5 部署全部服务，但该矩阵在任务类型均匀、source % 6 接入时理论命中率约 73%，与要求的 40%–60% 冲突。为优先满足制造多跳压力的目标，采用：

    edge 0,3: {0,1,2}
    edge 1,4: {2,3,4}
    edge 2:   {0,3}
    edge 5:   {1,4}

每类任务仍有 3–4 个边缘服务副本，实测接入边缘服务命中率为 53.00%。

## 未解决事项和实现边界

- 标准 shortest_path_fastest_resource 基线的目标就是优先最少跳数，因此其平均跳数不会随候选空间自动升到约 2；多跳激活应结合随机策略、两跳验证策略或训练后的 PPO 策略判断。
- 两跳验证策略是可行性诊断，不是新增论文基线，也不证明多跳策略优于单跳策略。
- smoke 只有 36 个任务，完成率差异不能作为“不下降”的统计结论；正式结论需要多随机种子同预算实验。
- deadline 松弛仅为多跳预留工程时间，没有在任务生成阶段精确计入未来所选路径。
- 直接执行 scripts/evaluate.py 时需要 PYTHONPATH=.；本次按现有调用约定完成验证，没有扩展任务范围修复脚本导入方式。

## 后续建议

- 使用相同任务流与随机种子对比原环境和新环境，并通过多种子均值、标准差或置信区间判断完成率是否显著下降。
- 分析 PPO 的目的边缘、资源类型和路径跳数联合分布，确认策略确实在计算收益与传输代价之间学习权衡。
